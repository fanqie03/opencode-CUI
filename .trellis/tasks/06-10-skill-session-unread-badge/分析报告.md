# 未读消息小红点方案分析报告

> 基于 `design.md` + `design_inner.md` + `prd.md`，从架构、数据、可靠性、复杂度四个维度分析。

---

## 一、优点

### 1. 零 DB 变更，无迁移风险

无 DDL，`last_read_seq` 和 `max_seq` 均不入 MySQL，由 Redis Hash `ss:unread:{userId}` 全权维护。上线无 schema migration，回滚无数据兼容负担。

### 2. 事件驱动 + 开闭原则，侵入极低

```
handleToolDone → 发布 ToolDoneEvent（仅+1行）
  → UnreadPushListener（新文件）→ Lua updateMaxSeq → 决定推送

reportRead → Lua markRead → return 1 → 发布 ReadReportedEvent
  → ReadReportedListener（新文件）→ 推送清除
```

现有 `GatewayMessageRouter` 不感知未读逻辑，只发布事件。新增逻辑全部在 Listener 中闭环，符合开闭原则。

### 3. Lua 原子操作，无竞态

`updateMaxSeq` 和 `markRead` 均为单 Lua 脚本原子执行。并发场景（同时收到消息 + 同时上报已读）下不会出现 HSET 和 HDEL 交错导致状态错乱。三态返回值（0/1/2）驱动发布决策，避免重复推送。

### 4. 自愈设计，无 DB 兜底

| 场景 | 行为 |
|------|------|
| Hash key 7d 过期 | `updateMaxSeq` 自动创建 key + HSET + EXPIRE，return 1 |
| Hash key 被 flush | `markRead` 自动创建空 key + EXPIRE，return 1 |
| 查询侧 key 不存在 | `HLEN` 返回 0 / `HMGET` 返回 nil |

全链路由 Lua 自愈，不需要 DB fallback 查询。

### 5. 复用现有基础设施，不重复造轮子

| 组件 | 来源 | 状态 |
|------|------|------|
| `MultiDeviceSyncService` + `CompositeMultiDeviceSyncService` | `06-15-multi-device-sync` | 已存在 |
| `WsMultiDeviceSyncService` | 同上 | 已存在 |
| `ImMultiDeviceSyncService`（AppNotifyRequest 类型化） | 同上 | 已存在 |
| `SyncType.SESSION_UNREAD` | 同上 | 已定义 |
| `RedisMessageBroker.publishToUser()` | 现有 | 复用 |
| `SkillStreamHandler.handleUserBroadcast` | 现有 | 不改动 |

新增代码量极小：2 个 Event record + 2 个 Listener + 1 个 Redis Service + 2 个端点 + 2 个 Service 方法 + `GatewayMessageRouter` +1 行。

### 6. 单一查询接口，sessionIds 可选

`POST /unread` 一个端点覆盖两种场景：不传参→全局未读数（HLEN），传 sessionIds→详情列表（HLEN+HMGET）。与会话列表接口解耦，前端按需调用。

### 7. 前后端职责清晰

| 职责 | 归属 |
|------|------|
| 已读游标追踪 | 前端（`readMessageSeq` 内存变量） |
| 已读判断 + 未读清除 | 服务端（Lua markRead） |
| 活跃会话/免打扰 | 前端自行判断 |
| 流式保护 | 前端（消息未完整渲染不推进游标） |

服务端不追踪"用户在看哪个会话"，一律推送，前端自行决策是否显示。降低了服务端状态管理复杂度。

### 8. SyncType 扩展性

新增业务类型（如 `SESSION_DELETED`）只需在 `SyncType` 枚举追加一项，接口和 Composite 无需修改。`syncContent` 为 `Map<String, Object>`，不同业务类型可携带不同字段。

## 二、缺点与风险

### 1. 纯 Redis 存储，无持久化保障（中高风险）

**问题**：未读状态完全依赖 Redis Hash（TTL 7d），无 MySQL 备份。Redis flush/迁移/主从切换丢数据后，所有未读状态丢失。

**影响**：
- 用户 A 已读会话 S 的 10 条消息，Redis flush 后→S 重新出现未读角标（因为新消息到达时 Lua 自愈创建 key，maxSeq 从当前消息开始算，历史已读信息不可恢复）
- 7d TTL 意味着长时间不活跃的会话未读状态会自然过期（用户可能已经忘了）

**缓解**：`readMessageSeq` 是前端内存变量本身就不持久化，跨设备/刷新的"已读"感知本就依赖多端同步推送。Redis 恢复后，下次消息到达时 Lua 自愈重建，影响范围是"当前未读但无新消息的会话"。

### 2. unreadCount 二态与 PRD 数字角标描述冲突（中风险）

**PRD 描述**："数字角标（超过 99 显示 99+）"
**设计实现**：`unreadCount` 仅取 0 或 1，前端只显示红点

**实际效果**：用户看到红点但不知道有几条未读。如果 3 个会话各有未读，视觉上无法区分优先级。PRD 的"数字角标"需求在当前设计中无法满足——需增加实际未读消息数的计算逻辑。

### 3. Map<String, Object> syncContent 缺乏编译期类型安全（低风险）

```java
Map.of(
    "welinkSessionId", sessionId.toString(),  // 拼写错误 → 静默错误
    "unreadCount", 1,
    "maxSeq", maxSeq,
    "assistantAccount", ...
)
```

`WsMultiDeviceSyncService` 中 `request.syncContent().get("welinkSessionId")` 和 Im 实现中整体序列化到 `notify_content`——如果 key 拼写不一致，ws/im 两端行为可能不同。建议至少定义 key 常量类。

### 4. UnreadPushListener 同步查 DB（低风险）

```java
int maxSeq = skillMessageRepository.findMaxSeqBySessionId(sessionId);
```

ToolDoneEvent 触发后，Listener 同步查询 DB 取 `maxSeq`。在消息刚落库的场景下通常能查到，但存在极端时序：事务未提交、读写分离延迟。当前架构下 `handleToolDone` 在事务内发布事件，Spring 默认同步执行 Listener，实际在同一事务上下文中，风险较低。

### 5. 硬删除会话残留 Hash field（低风险）

设计文档标注"无影响"，但长期运行后 `ss:unread:{userId}` Hash 中会累积已删除会话的 field。虽然单个 field 内存占用极小，但大量用户 × 大量已删除会话的累积效应不容忽视。7d TTL 仅覆盖整个 key 过期，不清理单个 field。

**建议**：`SessionDeletedEvent` 监听器中追加 `HDEL ss:unread:{userId} {sessionId}`。

### 6. 前端复杂度集中（中风险）

`useSkillSession.ts` 需要同时管理：
- `readMessageSeq` 追踪（跨多条消息的 max 计算）
- debounce 500ms 上报
- 流式状态判断（消息是否完整渲染）
- 启动/前台/WS 重连时拉取 `POST /unread`
- 侧边栏渲染时拉取详情
- 收到 `session.unread` 推送时更新

单一 hook 职责过重，建议拆分为 `useReadTracking` + `useUnreadBadge` 两个独立 hook。

### 7. 已读上报无频率限制（低风险）

debounce 500ms 仅在 `readMessageSeq` 变化时触发。如果攻击者快速切换会话导致频繁变化，仍会产生较高 QPS。建议服务端增加简单的用户级 Rate Limiting。

### 8. IM 模式 API URL 未配置时静默失败（低风险）

`ImMultiDeviceSyncService` 在 `apiUrl` 为空时直接 return。调用方（Listener）无感知，推送静默丢失。建议至少在 Listener 侧判断返回值或配置校验启动时 fail-fast。

## 三、综合评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构优雅度 | ★★★★☆ | 事件驱动 + 策略模式 + 自愈 Lua，职责清晰 |
| 实现复杂度 | ★★★☆☆ | 后端低（~8 个文件），前端偏高（readMessageSeq 追踪 + 流式保护） |
| 可靠性 | ★★★☆☆ | Lua 原子操作可靠，但纯 Redis 无持久化是核心短板 |
| 可扩展性 | ★★★★☆ | SyncType/SyncMode 扩展零改动 |
| 可运维性 | ★★★★☆ | 零 DB 变更、配置驱动 sync-mode、Lua 自愈降级 |

**总评**：方案整体设计合理，事件驱动 + Lua 原子操作 + 复用基础设施是亮点。核心短板是纯 Redis 存储无持久化（RPO=0），以及 `unreadCount` 二态与 PRD 数字角标需求不一致。建议在实现前确认：①数字角标是否降级为红点；②是否需要 Redis 持久化或 DB 备份；③硬删除会话的 field 清理策略。

## 四、改进建议

1. **`unreadCount` 升级为实际未读数**：`updateMaxSeq` 时计算 `newSeq - HMGET(sessionId)` 差值作为实际未读条数，而非固定 1
2. **定义 `UnreadSyncKeys` 常量类**：统一 `syncContent` 的 key 名称（`WELINK_SESSION_ID`、`UNREAD_COUNT`、`MAX_SEQ`、`ASSISTANT_ACCOUNT`），避免拼写错误
3. **`SessionDeletedEvent` 清理 Hash field**：`HDEL ss:unread:{userId} {sessionId}`
4. **`POST /{id}/read` 增加用户级限流**：Guava RateLimiter 或 Redis 令牌桶
5. **前端拆分 hook**：`useReadTracking`（readMessageSeq + debounce + 上报）+ `useUnreadBadge`（拉取 + 推送处理 + 角标状态）
6. **IM apiUrl 启动校验**：`ImMultiDeviceSyncService` 在 `@PostConstruct` 中检查配置，blank 时 log.warn 提示
